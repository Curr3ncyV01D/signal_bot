# 🗺 План разработки: Этап 4 (Экономика и Рост)

## 📦 Эпик 1: Платёжная инфраструктура и Внутренний Кошелёк
**Цель:** Создать надежную систему хранения баланса пользователя и интеграцию с CryptoPay для пополнения счёта в USDT.

### Задача 1: Слой данных и Ledger (Бухгалтерия)
Система не просто меняет цифру баланса, а записывает «чек» для каждой операции.
*   **Спринт 1.1: Модели данных (DB Models)**
    *   Обновление `User`: добавление поля `balance` (Float, default 0.0).
    *   Создание модели `Transaction`: `id`, `user_id`, `type` (DEPOSIT, WITHDRAW, REWARD), `amount`, `description`, `created_at`.
    *   Создание модели `Invoice`: `id`, `user_id`, `amount`, `crypto_pay_id`, `status` (PENDING, PAID, EXPIRED).
*   **Спринт 1.2: Атомарный CRUD (Data Safety)**
    *   Реализация функций изменения баланса. **Важно:** использование транзакций БД, чтобы нельзя было списать больше, чем есть на счету (защита от «double spending»).
    *   Логирование каждой операции в таблицу `transactions`.

### Задача 2: Интеграция CryptoPay API (Polling)
- **Библиотека:** aiocryptopay.
- **Метод:** Гибридный Polling.
- **Логика:**
    1. Фоновый воркер `payment_checker` в `main.py` опрашивает API Crypto Bot каждые 30 секунд для всех инвойсов со статусом `PENDING`.
    2. Хендлер кнопки «Проверить оплату» делает мгновенный запрос статуса одного конкретного инвойса.
*   **Спринт 2.1: CryptoPay Service**
    *   Написание обертки для API CryptoPay (создание счета, получение статуса).
    *   Реализация фонового воркера `payment_checker`, который раз в 30 секунд опрашивает активные инвойсы (или настройка Webhook).
*   **Спринт 2.2: Логика пополнения**
    *   При подтверждении оплаты от CryptoPay:
        1. Смена статуса инвойса в БД.
        2. Начисление суммы на `balance` пользователя.
        3. Создание записи в `transactions`.
        4. Уведомление пользователя в ЛС: «Баланс пополнен на X USDT».

### Задача 3: Интерфейс Кошелька (UI/UX)
*   **Спринт 3.1: Меню «Мой Кошелёк»**
    *   Кнопки: `[➕ Пополнить баланс]`, `[📊 История транзакций]`.
    *   Выбор суммы пополнения (пресеты: 20, 40, 100 USDT или свой ввод).
*   **Спринт 3.2: Обработка платежей**
    *   Генерация ссылки на оплату и показ её пользователю с кнопкой «Проверить оплату».

## 🤝 Эпик 2: Реферальная система и Магазин подписок
**Цель:** Реализовать витрину товаров и виральный механизм роста через вознаграждения.

### Задача 1: Реферальные связи
*   **Спринт 4.1: Binding (Связка)**
    *   Парсинг команды `/start ref_{id}`.
    *   Запись `referrer_id` в профиль новичка. 
    *   **Правило:** Юзер не может быть рефералом самого себя.
*   **Спринт 4.2: Партнёрский кабинет**
    *   Отображение реферальной ссылки в профиле.
    *   Статистика: «Приглашено: X человек», «Заработано: Y USDT».

### Задача 2: Механика вознаграждений (Rewards)
*   **Спринт 5.1: Referral Logic**
    *   Условие: При каждой покупке подписки рефералом, его пригласитель получает **15%** от суммы сделки на свой баланс.
    *   Автоматическое создание транзакции типа `REWARD` для пригласителя.
    *   Мгновенное уведомление пригласителю: «Ваш друг оплатил подписку! Вам начислено X USDT».

### Задача 3: Магазин подписок (Checkout)
*   **Спринт 6.1: Тарифная сетка**
    * 1 месяц (30 дней): 20.0
    * 2 месяца (60 дней): 40.0
    * 5 месяцев (150 дней): 100.0
*   **Спринт 6.2: Логика покупки с баланса**
    *   Проверка: `if user.balance >= tariff.price`.
    *   Действие: Списание средств -> Продление `subscription_end` -> Запись транзакции `WITHDRAW`.
    *   Автоматическая выдача ссылки в VIP-канал после покупки.

## 🛠 Технические требования (Infrastructure)
1.  **Конфигурация:** Все цены и % реферальных выплат вынесены в `config.py`.
2.  **Точность:** Использование `Decimal` или `Float` с округлением до 2 знаков для всех финансовых операций.
3.  **Безопасность:** Добавление Middleware, который проверяет статус подписки перед доступом к аналитическим функциям (уже частично есть, расширить).
