# План реализации: Переход на Hosted Checkout (CactusPay URL Mode)

## 1. Слой API и Клиента (`src/services/cactus_client.py`)
**Цель:** Убедиться, что клиент всегда отдает URL и корректно обрабатывает статусы.

*   **Аудит `create_payment`**: Убедиться, что метод возвращает объект, содержащий `url`. 
*   **Fallback-логика**: Если поле `requisite` пустое или содержит ошибку (как сейчас), клиент не должен генерировать исключение, он должен просто вернуть ответ с заполненным полем `url`.
*   **Mock-режим**: В `DEV_MODE` возвращать тестовую ссылку (например, `https://example.com/pay/mock`).

## 2. Слой хранения и интеллектуальное восстановление (Persistence & Recovery)

**Цель:** Обеспечить сохранность платежных ссылок и предотвратить дублирование заказов (Order Flooding).

### 2.1. Модификация CRUD-слоя (`src/database/crud/billing_service.py`)
*   **Метод `create_invoice`**:
    *   Принимает аргумент `address` (в него передаем `payment_url` от CactusPay).
    *   Обязательно записывает `expires_at` (текущее время + `config.CACTUS_INVOICE_LIFETIME_SEC`).
*   **Новый метод-хелпер `get_active_pending_invoice`**:
    *   *Сигнатура:* `(session, user_id, provider, days) -> Invoice | None`
    *   *Логика:* Ищет в БД инвойс, где `user_id` совпадает, `provider == 'CACTUS'`, `status == 'PENDING'` и `expires_at > now()`.
    *   *Зачем:* Перед тем как запрашивать новую ссылку у CactusPay, бот проверит: «А нет ли уже готовой?».

### 2.2. Изменение логики в хендлере (`src/bot/handlers/shop.py`)
*   **Рефакторинг `_start_cactus_payment_flow`**:
    1.  **Check DB:** Сначала вызываем `billing_service.get_active_pending_invoice`. 
    2.  **Reuse Logic:** Если инвойс найден — сразу берем ссылку из `invoice.address` и показываем её пользователю. **Пропускаем запрос к API CactusPay.**
    3.  **New Invoice Logic:** Если инвойс не найден (или просрочен) — выполняем реальный запрос `cactus_client.create_payment`, получаем новый URL и создаем новую запись в БД.

### 2.3. Синхронизация данных (Data Integrity)
*   **Учет Native-сумм:** При сохранении ссылки в `address`, мы также фиксируем в `amount_expected_native` сумму в рублях, которую выставил шлюз. Это позволит нам в будущем (в воркере) точно знать, на какую сумму был выставлен этот конкретный URL.
*   **Payload Safety:** В поле `payload` сохраняем JSON с зафиксированной ценой в USDT (`price_at_creation`). Даже если через 5 минут после генерации ссылки вы измените цены в конфиге, система начислит юзеру подписку по «старой» цене, которая была в момент клика.

### 2.4. Визуальный таймер (UX)
*   Поскольку мы храним `expires_at` в БД, мы можем в реальном времени считать, сколько минут осталось до «протухания» ссылки, и писать юзеру: *"Ваша персональная ссылка действительна еще 8 минут"*.

## 3. Пользовательский интерфейс (UI/UX)
**Цель:** Создать понятный «экран счета» вместо экрана с номером карты.

*   **`src/bot/handlers/shop.py` (Метод `_start_cactus_payment_flow`)**:
    1.  **Запрос**: Вызывает `cactus_client.create_payment`.
    2.  **Валидация**: Проверяет наличие `payment_response.url`. Если URL нет — выводит ошибку.
    3.  **Рендеринг**: Отправляет (или редактирует) сообщение, используя новый шаблон «Оплата через сайт».
    4.  **Таймер**: Вычисляет время до `expires_at` и выводит его юзеру.

*   **`src/bot/keyboards/billing_kb.py` (Метод `get_cactus_payment_kb`)**:
    *   Кнопка 1: `🔗 Перейти к оплате` (кнопка-ссылка на URL).
    *   Кнопка 2: `✅ Я оплатил` (callback для мгновенного запуска `process_payment_update`).
    *   Кнопка 3: `⬅️ Назад` (возврат к выбору тарифа).

## 4. Локализация (`assets/locales/ru/messages.ftl`)
**Цель:** Объяснить пользователю, что делать.

*   **Ключ `shop-cactus-pay-hosted-screen`**:
    > 🧾 **Счет на оплату: { $plan_label }**
    >
    > Для активации доступа перейдите на защищенную страницу оплаты CactusPay. Там вы сможете выбрать удобный способ: **Карта РФ**, **СБП** или **QR-код**.
    >
    > 💰 **К оплате:** { $amount_rub } RUB
    > 💎 **Будет зачислено:** { $amount_usdt } USDT
    >
    > ⏳ Ссылка действительна: **{ $countdown }**
    >
    > _После оплаты в терминале подписка активируется в боте автоматически в течение минуты._

## 5. Слой автоматизации (Worker)
**Цель:** Сохранение «магии» автоматического включения.

*   **`src/services/payment_worker.py`**:
    *   Логика остается **без изменений**. Воркер всё так же опрашивает API CactusPay по `external_id`. 
    *   Как только Cactus подтвердит, что юзер оплатил счет на сайте, наш `BillingProcessor` получит статус `ACCEPT` и выдаст подписку.

# Подводные камни (Senior Notes для Trae)

1.  **Price at Creation**: Убедись, что в `payload` инвойса сохраняется `u` (цена в USDT на момент создания), чтобы при скачке курса в конфиге юзер не получил «недоплату» после оплаты счета.
2.  **Handling 'WAIT' status**: CactusPay может держать статус `WAIT` (ожидание) дольше обычного. Убедись, что бот при нажатии «Я оплатил» корректно выводит: *"⏳ Транзакция обрабатывается шлюзом, подождите немного"*.
3.  **HTML Parse Mode**: При выводе ссылки в кнопке убедись, что URL валидный и не содержит спецсимволов, ломающих разметку Telegram.
4.  **Concurrency**: Если юзер нажмет кнопку «Я оплатил» 5 раз подряд, Redis-лок в `BillingProcessor` должен отсечь лишние запросы.
