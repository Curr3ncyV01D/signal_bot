# План реализации: MCAP Healing (Sprints 1-3)

## Фаза 1: Слой хранения (Database & Schema)
**Цель:** Создать гибкую систему переопределения тикеров без изменения кода.

1.  **`src/database/models.py`**:
    *   Создать модель `CoinMapping`.
    *   **Поля:**
        *   `symbol`: `String(20)` (Primary Key) — Тикер Bybit (например, `WLD`).
        *   `cg_id`: `String(100)` (Index) — Уникальный ID CoinGecko (например, `worldcoin-org`).
        *   `comment`: `String(255)` (Optional) — Заметка для админа.
2.  **Alembic**: Генерация и применение миграции.
3.  **Первичное наполнение**: Перенести данные из `utils.MANUAL_MAPPING` в новую таблицу через SQL.

## Фаза 2: Реформа маппинга (Smart ID Resolver)
**Цель:** Решить проблему коллизий (одинаковых тикеров) через проверку рыночного веса.

1.  **`src/services/supply_worker.py` (Смена Ingestion)**:
    *   **Удалить** `target_symbols = list(market_aggregator.snapshots.keys())`.
    *   Внедрить SQL-запрос: Получать список всех уникальных symbol из таблицы CoinFundamental.
    *   **Результат:** Воркер работает автономно, опираясь на накопленные в БД данные.

## Фаза 3: Решение проблемы «Холодного старта»
**Цель:** Обеспечить 100% покрытие всех монет Bybit сразу после запуска.

1.  **`src/services/supply_worker.py` (ШАГ 2 - Смена источника)**:
    *   **Удалить** зависимость от `market_aggregator.snapshots.keys()`.
    *   В начале цикла воркера внедрить вызов Bybit HTTP API (метод `get_instruments_info`), чтобы получить **полный список торгуемых USDT-пар** (аналогично тому, как это делает `BybitListener`).
    *   **Результат:** Воркер будет знать о существовании всех 600+ монет Bybit, даже если по ним еще не прилетало данных в WebSocket.

## Фаза 4: Интеграция Overrides
**Цель:** Приоритет ручных настроек над автоматикой.

1.  **`src/services/supply_worker.py` (ШАГ 3 - Объединение)**:
    *   Реализовать чтение таблицы `CoinMapping` при каждом запуске воркера.
    *   **Приоритет маппинга:**
        1.  `CoinMapping` (БД) — Высший приоритет.
        2.  Smart Top-250 (Markets API) — Средний приоритет.
        3.  Coins List (Public API) — Fallback (если ничего не помогло).

## Фаза 5: Оптимизация сетевых запросов (Rate Limits)
**Цель:** Избежать 429 ошибок и обеспечить стабильное обновление.

1.  **`src/services/supply_worker.py`**:
    *   Внедрить экспоненциальную задержку (Exponential Backoff) при получении 429 статуса.
    *   Добавить логирование пропущенных монет в конце цикла: «*Не удалось найти MCAP для: PEPE2, NEWCOIN*». Это будет сигналом для тебя добавить их в `CoinMapping` вручную.

# Подводные камни (Senior Notes для Trae)

1.  **Case Sensitivity**: Bybit шлет тикеры в верхнем регистре (`BTC`), CoinGecko — в нижнем (`btc`). Воркер должен всегда нормализовать всё к нижнему регистру перед сравнением.
2.  **Atomic Upsert**: При сохранении данных в `CoinFundamental` использовать `ON CONFLICT (symbol) DO UPDATE`, чтобы не плодить дубликаты.


# План реализации: Автоматическое расширение охвата MCAP (Phase 4-5)

## Фаза 4: «Посев» данных (Initial Seeding)
**Цель:** Синхронизировать состав таблицы `coin_fundamentals` с актуальным списком инструментов Bybit при старте системы.

1.  **`src/database/crud/fundamentals_service.py`**:
    *   Реализовать метод `seed_coin_fundamentals(session, symbols: list[str])`.
    *   **Логика:** Принимает список тикеров (например, 617 штук). Выполняет `INSERT ... ON CONFLICT (symbol) DO NOTHING`.
    *   **Результат:** Все монеты, о которых знает Bybit, теперь гарантированно имеют строку в нашей БД (пусть даже с нулевым supply на старте).

2.  **`src/main.py` (Точка входа)**:
    *   В блоке инициализации (Шаг 2 «Прогрев данных») вызвать `seed_coin_fundamentals`, передав туда полный список `target_symbols`, полученный от `BybitListener`.
    *   Это нужно сделать **ДО** запуска `supply_sync_worker`.

---

## Фаза 5: Динамическое обнаружение (Real-time Sync)
**Цель:** Гарантировать, что новые листинги (монеты, появившиеся после запуска бота) сразу попадают в очередь на получение MCAP.

1.  **`src/services/symbol_sync.py` (Воркер листингов)**:
    *   Внутри цикла, когда обнаружены `new_symbols` (монеты, которых нет в текущем наборе сокетов):
    *   Добавить вызов `seed_coin_fundamentals(session, new_symbols)`.
    *   **Результат:** Как только Bybit добавляет новую монету, она мгновенно регистрируется в БД. `supply_worker` увидит её при следующем проходе (через 12 часов) или при перезагрузке.

---

## Фаза 6: Оптимизация Supply Worker (The Resolver)
**Цель:** Улучшить обработку ошибок и визуальный контроль.

1.  **`src/services/supply_worker.py`**:
    *   **Обработка «Пустышек»:** Убедиться, что воркер в первую очередь пытается обработать монеты, у которых `circulating_supply IS NULL` или `0`.
    *   **Логика уведомлений:** В конце цикла воркер должен выводить в лог список монет, для которых **не удалось** найти ID на CoinGecko (Unmapped Symbols).
    *   **Пример лога:** `[MCAP] Внимание! Не найден маппинг для: MEW, CAT, 1000PEPE2. Добавьте их в таблицу coin_mapping.`

---

Обнаружили причину, по которой Market Cap обновляется только для 300 монет из 600+. Воркер эмиссии берет список из БД, но новые монеты Bybit в эту таблицу не попадают автоматически. Нам нужно реализовать логику «Посева» (Seeding).

**Выполни следующие задачи:**

1. **Создай метод Seeding в CRUD:**
   - В `src/database/crud/fundamentals_service.py`реализуй асинхронную функцию `sync_coin_fundamentals_list(session, symbols: list[str])`.
   - Она должна выполнять Bulk Insert (пачкой) всех переданных символов в таблицу `coin_fundamentals`. Используй `ON CONFLICT (symbol) DO NOTHING`, чтобы не трогать существующие записи.

2. **Интегрируй Seeding при старте (`main.py`):**
   - В `main.py`, в блоке загрузки фундаментальных данных, после получения `target_symbols` от лисенера, вызови созданную функцию синхронизации. Мы должны гарантировать, что таблица `coin_fundamentals` содержит все 600+ монет Bybit до начала работы воркеров.

3. **Интегрируй Seeding в Real-time (`symbol_sync.py`):**
   - В воркере `symbol_sync_worker`, когда обнаруживаются новые монеты (`new_symbols`), также вызывай `sync_coin_fundamentals_list`, чтобы они сразу попадали в БД.

4. **Supply Worker Reporting:**
   - В `supply_worker.py` добавь финальный лог в конце цикла обновления. Он должен выводить список символов, для которых **не удалось** найти `cg_id` (те, что остались `unresolved`). Это поможет нам вручную добавлять маппинги.

**Результат:** База данных должна автоматически наполняться всеми тикерами с биржи, а воркер эмиссии — подхватывать их и искать Market Cap.
