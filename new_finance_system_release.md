## 1. Спецификация Протокола Payload (Data Contract)
Для исключения ошибок парсинга и контроля параметров сделки на момент её инициализации внедряется строгая схема Payload.

*   **Формат хранения:** Строгий JSON-объект в БД.
*   **Схема Payload:** `{"a": str, "d": int, "p": float}`
    *   `a` (action): действие (например, `"sub"` / `"buy_sub"`).
    *   `d` (days): количество дней подписки.
    *   `p` (price_at_create): цена тарифа в USDT на момент создания инвойса (используется для логирования и контроля изменений цен).
*   **Legacy-адаптер (`_parse_payload` в `billing_service.py`):**
    При обработке старых записей или незавершенных транзакций парсер сначала пробует выполнить `orjson.loads()` / `json.loads()`. В случае неудачи (например, `JSONDecodeError`) применяется резервное регулярное выражение для поиска паттерна `sub_(\d+)`, переводящее его в унифицированный формат: `{"a": "sub", "d": days}`.

## 2. Фаза 4 — Трансформация UI/UX (Target-Action Flow)
**Цель:** Перевести интерфейс на модель «целевого действия» (Target-Action), полностью убрав ручное пополнение баланса как изолированный шаг.

**Файлы для изменений:** `src/bot/handlers/shop.py`, `src/bot/keyboards/billing_kb.py`.

### 2.1. Рефакторинг процесса покупки (хендлер `buy_plan_{days}` / `callback_process_purchase`):
1.  **Захват цены:** Извлечение актуальной стоимости тарифа из конфигурационного файла: `price = config.TARIFFS.get(days)`.
2.  **Проверка кошелька:** Получение текущего баланса пользователя: `current_balance = user.balance`.
3.  **Ветвление логики (Branching):**
    *   **Сценарий А (Баланса достаточно):**
        *   Если `current_balance >= price`, пользователю выводится экран подтверждения списания средств.
        *   При подтверждении вызывается `billing_service.purchase_subscription(...)`.
        *   Отображается финальный экран успеха.
    *   **Сценарий Б (Требуется доплата):**
        *   Рассчитывается сумма доплаты: `amount_to_pay = price - current_balance`.
        *   Формируется JSON-payload: `{"a": "sub", "d": days, "p": price}`.
        *   Вызывается `cryptomus_client.create_payment` на сумму `amount_to_pay`.
        *   Пользователю отправляется сообщение с реквизитами:
            *   Адрес кошелька в теге `<code>` для быстрого копирования в один тап.
            *   Указание сети (например, *TRC-20* / *TON*).
            *   Сгенерированный QR-код (если поддерживается шлюзом).
            *   Текст сообщения: *«У вас есть {current_balance} USDT. Для активации тарифа на {days} дней необходимо доплатить {amount_to_pay} USDT»*.
4.  **Очистка Legacy-интерфейса:**
    *   Полностью удалить кнопки «Пополнить баланс» и связанные с ними цепочки хендлеров ввода произвольной суммы.
    *   Пополнение теперь возможно только внутри контекста покупки конкретного тарифа.
    *   **Заметка по реализации:** вместо жесткого удаления всех legacy callback-цепочек `deposit` сразу сохранен compatibility redirect на экран выбора тарифа. Причина: в уже отправленных пользователям сообщениях могли остаться старые inline-кнопки, и их мгновенное удаление создало бы dead-end UX и ложные ошибки при нажатии на исторические сообщения.

### 2.2. Изменения в клавиатурах (`billing_kb.py`):
*   Удалить клавиатуры для ручного ввода сумм депозита.
*   Добавить под экран оплаты кнопку **«Проверить оплату»**, привязанную по callback к `external_id` инвойса.
*   Добавить кнопку-ссылку на инструкцию «Как оплатить картой» для снижения порога входа.

## 3. Фаза 5 — Автоматизация и Фоновый Воркер (Activation Chain)
**Цель:** Обеспечить автоматическое начисление подписки и баланса без обязательного участия пользователя.

**Файлы для изменений:** `src/database/crud/billing_service.py`, `src/services/payment_worker.py`.

### 3.1. Логика `verify_and_activate_payment`:
Метод является критической секцией и должен выполняться атомарно («Всё или Ничего»).
1.  **Lock:** Захват Redis-лока по `user_id` / `invoice_id` (предотвращает Race Conditions при одновременном нажатии кнопки пользователем и срабатывании фонового воркера).
2.  **Sync:** Запрос актуального статуса платежа в API Cryptomus через `CryptomusClient.get_status`.
3.  **Credit:** Если транзакция перешла в статус `PAID` или `PAID_OVER`:
    *   Сумма фактического поступления `amount_actual` начисляется на `user.balance`.
    *   Создается запись транзакции `Transaction(type='DEPOSIT')`.
4.  **Intent Execution (Цепочка выполнения намерения):**
    *   Парсинг сохраненного в инвойсе `payload`.
    *   Если `action == "sub"`:
        *   Проверяется актуальный баланс пользователя.
        *   Если `balance >= config.TARIFFS[days]` (цена берется строго из конфига для защиты от подмены):
            *   Вызывается `purchase_subscription` / `activate_subscription_logic`.
            *   Создается запись транзакции `Transaction(type='WITHDRAW')`.
            *   В результирующий объект `PaymentVerificationResult` передается флаг `auto_activated=True`.
5.  **Commit & Cache Invalidation:** Фиксация транзакции в базе данных и вызов `invalidate_user_cache(user_id)` для мгновенного обновления прав доступа пользователя в системе.
6.  **Fail-safe:** Если подписка не активировалась (например, изменился тариф), средства в обязательном порядке остаются на балансе пользователя.

### 3.2. Логика Smart Polling Worker (`payment_worker.py`):
Фоновый процесс регулярно опрашивает платежный шлюз по незавершенным счетам.
*   **Выборка:** Опрашиваются только счета со статусом `PENDING` или `PARTIAL`.
*   **Адаптивные интервалы (Smart Polling):**
    *   Счета возрастом < 15 минут проверяются каждые 30 секунд.
    *   Счета возрастом > 15 минут проверяются раз в 2–5 минут.
*   **Группировка запросов:** Использование `asyncio.gather` с ограничением конкурентности через `asyncio.Semaphore(5)`, чтобы избежать лимитов (rate limits) API Cryptomus.
*   **Авто-отмена:** Инвойсы без активности автоматически переводятся в статус `EXPIRED` через 120 минут.
*   **Заметка по реализации:** адаптивный Smart Polling реализован через in-memory расписание воркера (`next_poll_at`), а не через отдельную колонку БД. Причина: это позволяет не расширять схему `invoices` ради временного технического состояния опроса и не тащить миграцию для эфемерной логики планировщика.

## 4. Обработка граничных случаев (Edge Cases) & Безопасность

1.  **Недоплата (Статус `PARTIAL`):**
    *   Если сумма транзакции меньше необходимой, воркер зачисляет фактически пришедшие средства на баланс пользователя.
    *   Статус инвойса в БД обновляется на `PARTIAL`.
    *   Бот отправляет уведомление: *«Получено X USDT. Для активации тарифа необходимо доплатить еще Y USDT на тот же адрес»*. Намерение (`payload`) сохраняется до полной оплаты или истечения времени жизни инвойса.
2.  **Погрешность сети (Payment Tolerance):**
    *   Внедрить константу `config.PAYMENT_TOLERANCE_USD = 0.5`. Если сумма недоплаты не превышает этот лимит, платеж засчитывается как успешный (`PAID`) для повышения лояльности клиентов при небольших отклонениях в комиссиях бирж.
3.  **Переплата (Статус `PAID_OVER`):**
    *   Намерение выполняется (активируется тариф), а излишек сверх цены тарифа остается на `user.balance` для будущих покупок.
4.  **Изменение тарифов «на лету»:**
    *   Если администратор изменил `config.TARIFFS` в процессе оплаты, и зачисленных средств стало недостаточно для автоматического списания: деньги остаются на балансе пользователя, а бот уведомляет: *«Цены обновились, средств на балансе не хватает для авто-активации. Пожалуйста, проверьте меню тарифов»*.
5.  **Идемпотентность:**
    *   Перед запуском цепочки активации обязательно проверяется текущий статус инвойса в БД. Если он уже отмечен как `PAID`, обработка немедленно прекращается.
6.  **Логирование переходов:**
    *   Каждое изменение статуса счета (`PENDING` -> `PARTIAL` -> `PAID`) фиксируется в таблице `UserEvent` для последующего анализа конверсии воронки оплат.
